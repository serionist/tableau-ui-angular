Server-side rendering

Every component renders on the server; what needs a screen waits for the browser.

The components render on the server

No component touches window or document while it renders, so an app can render its pages on a server or prerender them at build time. This site prerenders every page, with the components on it, and its build fails when a page throws while it renders. These are its own server files:

What waits for the browser

The server has no layout and no user, so what measures, observes or asks the browser starts after the first render there.

What On the server
The table and tab-virtualize They render without rows: load() and reload() measure first, so on the server they load nothing and resolve false . Call load() once the view is drawn, as the table page does.
The Monaco editor Monaco loads, and the editor is created, after the first render in the browser.
ThemeService.initialize() It does nothing, so the server's page is light at the default font size; the browser then applies the user's stored theme.
The form field, the arrow scroll, the tab group, the tree, the menu button group, the resize watcher They measure and observe after the first render, in the browser only.
ClipboardService It uses navigator.clipboard : call it from what the user does, such as a click, never while rendering.

Dialogs and snacks on the server

Their services show nothing on the server, and answer so that code waiting on them goes on.

Method On the server
DialogService 's openModal() , openTemplateModal() , openDialog() , openTemplateDialog() A DialogRef for a dialog that is never shown; closing it still emits closed$ .
openConfirmationMessageDialog() , openConfirmationTemplateDialog() They resolve false at once, so a guard or a resolver that awaits one doesn't hold the render.
SnackService 's openSnack() , openSnackWithAction() , openSnackFromTemplate() , openSnackComponent() A SnackRef for a snack that is never shown.

Hydration

Hydration isn't wired yet. The library isn't tested with it, and this site doesn't call provideClientHydration() , so the browser renders each page again over the server's HTML.
